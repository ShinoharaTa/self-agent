## 0. 何のために・結論

**何のために**: オーナーはいくつもの作業を並べて任せる。1 つずつ開いて回らずに、右腕（#inbox）に訊けば全体が分かり、終わった・止まったを右腕の所で知り、右腕に言えば相手に届くようにする。

**結論**
- 推しは **案 A（台帳と知らせはアプリが作る）を先に、案 B のうち「届ける」「配る」だけを後から 1 回の再起動で足す**。案 C（右腕が自分で見回る）は作らない。
- 最初の 3 段（L1〜L3）は **ツールの定義とシステムプロンプトに触らない**（キャッシュは外れない）。
- いちばん大きい発見: **今は話題のターンが同時に 1 つしか動かない見込み**で、**許可・質問を待っている話題が枠をふさぐ**。順番待ちの話題は一覧で「動いていない」に見える（§1.4）。「並列で任せる」の体感は、まずここを見えるようにしないと良くならない。
- 外部サービスは増えない（運用コスト 0 円。§9）。

### 1.2 後追いの指示を送る口

- **右腕から、既にある話題へ送る口は無い**【確】。設計でも「既にある話題への代筆は作らない。右腕は札で案内し、オーナーがそこに打つ」と決めてある【文 v3 §4】。
- 部品は在る: `handler.submitText({..., via: "right_hand"})`【確 `app/handler.ts`】。今は `session_open` の最初の依頼だけが使う。投稿の頭は「（右腕から）」、本文の URL は WebFetch の許可に入れない。**`via` は履歴に残らない**（owner の行の source は web）。
- 動いている話題に送った発言は **そのターンが終わるまで待つ**（同じチャンネルは直列【確 `app/queue.ts`】）。ターンの途中に割り込む口は無い（［中断］だけ）。

### 1.3 終わった・あなたの番を右腕が知る経路

- **無い**【確】。話題の返事はその話題のチャンネルに出るだけで、#inbox にも右腕の会話（SDK の文脈）にも何も入らない。右腕が知るのは、オーナーに訊かれて `topic_list` を呼んだときの状態だけ【文 v3 §4「右腕は結果を待たない・受け取らない」】。
- オーナーが知る経路: 許可・質問はその話題のチャンネル（メンションで鳴る）と Web の「あなたの番」【文 REQUIREMENTS の通知】。**終わった** は Web の未読の点（最後の行が返事）と、Discord のその話題への返信だけ。
- 右腕が始めたターンの返事は、Bot 自身の「（右腕から）」の投稿への返信になる【確】。**オーナーには鳴らない見込み**【推。`repliedUser` は返信先の書き手に効くため】。つまり右腕に任せた作業ほど、終わりに気づきにくい。

### 1.4 同時に動けるターンの数

- 全体の上限は `SELF_AGENT_MAX_CONCURRENT`（既定 2）。**話題（セッションのチャンネル）のターンはそのうち `max(1, 上限 - 1)` = 既定で 1 つ**。残り 1 つは #inbox・#tasks 用。`SELF_AGENT_SHELL=1` なら上限を上げても話題は 1 つ【確 `app/queue.ts`・`config.ts`】。本番の値は読んでいない【未】。
- **許可・質問を待っているターンは枠を持ったまま**【推。待ちは `runChannelTurn` の中で、キューの枠の中】。待ちは許可 300 秒・質問 900 秒まで（既定。切れたら deny）で、その間ほかの話題は始まらない。
- 枠を待っている話題は `runningTurns` に出ない【確 `handler.ts`: 枠を取ってから登録】。だから一覧では running でなく idle に見える。`KeyedSerialQueue.has(channelId)` で順番待ちは分かる【確】（/mode の検査 `app/session-mode.ts` が既に使っている【確】）。
- 1 つの話題の中では、プロジェクトのセッションはサブエージェント（Agent）とバックグラウンドの実行を使える【確 `project-profile.ts`: 禁じていない・`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` を外す】。今の「並列」の実体は、話題の数ではなく話題の中のこれ。

### 1.5 端末のセッションの状態（#456）

- `sessionState`【確 `cc/registry.ts`】: 保留中の許可・status waiting・（hook の判断待ち かつ busy でない）→ needs_input ／ **status busy → running** ／ ほかは idle。status は `claude agents --json` の値そのまま。
- バックグラウンドのタスクが残ると status は busy のまま【文 #456。40 時間動きの無いセッションが実行中に並ぶ】。`lastActivity`（最後の指示・hook の事象・記録の最後の行）は別に持っている【確】ので、「busy だが最後の事象が Stop で、その後に指示が無い」は見分けられる材料が在る。#456 のうち、入力欄の下のエージェントの一覧で届かない件は #458 で直した。端末のセッションの一覧の表示が作業中のままに見える件は残る（この案では触らない）。
- プロジェクトのセッションで、バックグラウンドのタスクを残したままターンが終わったとき何が起きるかは確かめていない【未】。

## 3. 案

### 案 A: 台帳と知らせはアプリが作る（右腕は読むだけ）

- **足す物**: (1) 一覧の状態を増やす（順番待ち・止まった・終わり方・かかった時間・右腕が始めた印）。`topic_list` の**結果の中身**と `/api/topics` に足す。(2) ターンの終わりをアプリが拾い、決まった文のまとめを **#inbox に 1 通**（既定の人格の Bot。履歴には notice の行 → Web の右腕の会話にも出る）。LLM は通さない。(3) 予約した依頼のターンで `topic_list` を使えるようにする（処理の側だけ）。
- **届ける・配る**: 足さない（今の決定のまま。まとめの行からその話題を開いて、オーナーが書く）。
- ツール・システムプロンプト: **変えない**（結果の欄が増えるだけ。定義・説明の文は同じ）。DB: **変えない**（履歴の連番と `outcome`、`sessions.origin` で足りる）。キャッシュ: 外れない。再起動: 要る（段ごと）。大きさ: **中**。
- **弱い所**: 「右腕に言えば届く」が無い。まとめは決まった文で、中身（何が分かったか）は言わない。右腕の文脈には入らないので、右腕は訊かれるたびに `topic_list` を呼ぶ。

### 案 B: 右腕に手を足す（ツールで届ける・配る・読む）

- **足す物**: `topic_send {topic, text}`（既にある話題へ `submitText` の `via: right_hand` で届ける）、`session_open` を 1 発言に複数、`topic_read {topic}`（最後の返事の頭を読む）、システムプロンプトに統括の数行。
- ツール・システムプロンプト: **変える**。DB: `history` に `via` の列 1 つ（誰が届けたかを残す。次に空いている版。v48 は #507 の `topic_pins` が使った）。キャッシュ: **全セッションで 1 回外れる**（軽いモードもプロジェクトのセッションも）。再起動: 1 回にまとめる。大きさ: **中〜大**。
- **弱い所**: 右腕が動くのはオーナーが話しかけたときだけ（知らせは来ない）。`topic_read` は担当の返事（リポジトリや Web の中身を含みうる）を右腕の文脈に入れるので、v3 の「右腕は結果を受け取らない」（サブエージェントに当たらない理由）を崩し、中の指示に従って `topic_send` する道ができる。v3 §4 の「代筆は作らない」を覆す。

### 案 C: 右腕が自分で見回る（事象で右腕のターンを起こす）

- **足す物**: 話題が終わった・止まったとき、アプリが #inbox に「任せた作業の動き: …」のターンを自動で 1 つ入れ、右腕が読んで（`topic_read`）自分の言葉でまとめ、次の手を提案する。予約した依頼の、事象で起きる版。
- ツール・システムプロンプト: **変える**（見出しの説明・自動のターンの決まり）。DB: 事象の表 1 つ。キャッシュ: 1 回外れる。再起動: 1 回。大きさ: **大**。
- **弱い所**: オーナーが頼んでいないターンで利用枠を使う（1 件終わるごとに #inbox の 1 ターン）。#inbox の文脈が担当の中身で膨らむ。自動のターンが送る → 終わる → また自動のターン、の輪を止める歯止めが要る。#449 の「担当が自分から上げる」（後で、と決めた）と #337 を先取りする。

## 4. 推しと段

**推し: A を先に入れ、B から `topic_send` と「1 発言に複数」だけを 1 回の再起動で足す。`topic_read` と案 C は作らない。**

### L4（要点。決定 1 は c（届ける。確認なし）。5・6 は推しの場合）
